## Recommendation

**Deploy on Cloudflare Workers.**

The project already ships with the `@astrojs/cloudflare` adapter wired into `astro.config.mjs` — Cloudflare requires zero migration cost, unlike every alternative researched. It scored a clean pass on all five agent-friendly criteria (CLI-first via `wrangler`, fully serverless, GitHub-hosted `llms.txt` docs, deterministic `wrangler deploy`/`rollback`, and GA remote MCP servers), matches the developer's stated existing familiarity with Cloudflare, and its free tier (100k requests/day) comfortably covers the PRD's low-QPS, small-data-volume MVP scale. No persistent connections are required (confirmed in the interview), so Workers' request/response model is not a constraint. External Supabase (auth/DB) and OpenRouter (AI generation) mean co-located managed services were not a factor in scoring.

Notes per platform:

- **Cloudflare Workers**: Cloudflare's own docs confirm the Astro adapter *no longer supports* deployment to Pages — Workers is the sole supported path for Astro today, which is exactly the path already configured. `nodejs_compat` is default for compatibility dates ≥2026-08-04. `wrangler` covers the full operational loop (`deploy`, `rollback`, `tail`, `secret put`) and two GA remote MCP servers (bindings, observability) give structured agent access.
- **Vercel**: `@astrojs/vercel` targets Node serverless functions by default (Edge adapter removed, edge is opt-in for middleware only). CLI and docs are equally strong to Cloudflare's. Vercel MCP is public beta (OAuth-backed). Hobby (free) tier is licensed "personal use only" — a real constraint if the project moves beyond a private MVP.
- **Render**: Native Node Web Service, no Docker. GA MCP server (20+ tools) is a standout. Scores Partial on "managed/serverless" because Web Services are always-on long-lived processes, not scale-to-zero functions — free tier cold-starts 30-60s and is explicitly called out by Render as non-production-grade, so a paid Starter tier (~$7/mo) would be needed.
- **Netlify**: Functions-based SSR, matches the adapter model, but rollback is dashboard-only (no CLI verb found) and the newly-launched MCP server's maturity is unverified.
- **Railway**: No free tier since 2023 (usage-billed from a $5 trial credit). Railpack (2025 successor to Nixpacks) has build-detection behavior that isn't fully documented as GA. Official MCP server and Claude Code plugin are a strong integration signal, but not enough to offset build-stability uncertainty for a 3-week MVP timeline.
- **Fly.io**: Full container control and true persistent-process support, neither of which this project needs. Dockerfile is a mandatory artifact (even though `fly launch` auto-generates one), pulling in operational surface explicitly out of scope for this MVP. Docs format is markdown-flavored ERB, not clean markdown/MDX.

### Shortlisted Platforms

#### 1. Cloudflare Workers (Recommended)

Already the configured adapter — zero migration cost. Clean sweep on all five criteria. Matches developer's existing familiarity (stated in interview). Free tier comfortably covers PRD scale (medium user count, low QPS). No persistent-connection requirement to work around.

#### 2. Vercel

Near-identical CLI/docs/deploy-API strength to Cloudflare. Would require swapping the adapter (`@astrojs/cloudflare` → `@astrojs/vercel`) and re-validating the SSR build — a real but bounded cost. MCP is beta rather than GA. Hobby tier's "personal use only" licensing is worth flagging if the project's status changes.

#### 3. Render

Simplest mental model of the shortlist — a plain long-lived Node process, no edge-runtime semantics to reason about, and a GA MCP server. Loses to Cloudflare/Vercel on the "managed/serverless" criterion (not scale-to-zero) and requires a paid always-on tier from day one since the free tier is not viable for a user-facing app. Full adapter swap to `@astrojs/node` required.

## Anti-Bias Cross-Check: Cloudflare Workers

### Devil's Advocate — Weaknesses

1. **CPU-time billing model on the AI-generation path.** Workers bills (and free-tier-limits) CPU-time, not wall-clock time. The OpenRouter call itself is I/O wait, but any non-trivial parsing/validation of LLM output done synchronously in the request handler counts against the CPU-ms budget (10ms/request on free tier). A flashcard-generation flow that does JSON parsing, validation, and retry logic risks silently hitting this ceiling under larger pasted-text inputs, especially before the project has load-tested realistic payloads.
2. **Live `astro:env` / `wrangler.jsonc` vars mismatch.** Confirmed via research as an open GitHub issue (withastro/astro#16790): `astro:env` doesn't reliably forward `wrangler.jsonc` `vars` to the runtime. This project's `astro.config.mjs` already declares `SUPABASE_URL`/`SUPABASE_KEY` via `envField` — meaning this isn't a hypothetical edge case, it directly touches this project's existing env-var wiring and could cause silent auth misconfiguration.
3. **Workers-specific vendor lock-in via bindings.** As the app grows (e.g., adopting Astro's Sessions API, which auto-provisions KV), Cloudflare-specific bindings creep into the codebase. The "we can switch platforms later" assumption gets costlier with every binding added, unlike a plain Node app that stays portable.
4. **`nodejs_compat` is broad, not 100% Node parity.** Native bindings, some filesystem-heavy or child-process-dependent npm packages can still fail on Workers even with `nodejs_compat_v2` enabled — a package added later (e.g. for richer text/PDF parsing, if scope ever grows past "paste text only") could silently break in production while working in a local Node-based test.
5. **Local dev doesn't perfectly emulate production isolates.** `wrangler dev` / `astro dev` diverge from the real Workers V8-isolate runtime in edge cases (module resolution, some Node built-ins, timing characteristics) — "works in local preview" is not a complete guarantee of "works in production."

### Pre-Mortem — How This Could Fail

The team deployed 10xCards's Astro SSR app on Cloudflare Workers assuming "it's already the adapter, it'll just work." Early smoke tests passed locally with `wrangler dev`, so no one probed the gap between local emulation and the real edge runtime. Three weeks in, users reported flashcard generation silently failing for longer pasted texts — the LLM-response parsing loop, written straightforwardly, occasionally exceeded the CPU-time ceiling under bursty traffic, and Workers killed the request without a clear client-side error, just a blank state. Nobody had budgeted time to profile CPU-ms per request because the free-tier limits felt generous during solo testing with small inputs. Separately, the `astro:env`/wrangler-vars mismatch meant a `SUPABASE_KEY` rotation done through the Cloudflare dashboard didn't propagate the way the team expected, causing a silent auth outage that took hours to diagnose because logs read as if the key were present. What looked like "no infrastructure to manage" quietly became "infrastructure whose failure modes are invisible until they aren't."

### Unknown Unknowns

- Workers' request/response body-size limits and streaming behavior can subtly differ from a traditional Node server's — large pasted-text inputs near size limits may behave differently than local dev suggests.
- The `compatibility_date` field silently opts a Worker into new default runtime behaviors on every bump (e.g. `nodejs_compat` became default for dates ≥2026-08-04, confirmed during this research) — a `compatibility_date` change made for an unrelated reason can quietly shift runtime semantics.
- Preview/branch deployments on Workers don't come with the same one-click PR-preview-URL convention Vercel/Netlify provide out of the box via GitHub integration — this needs to be wired up manually via Wrangler environments/versions.
- Workers' isolate-based debugging surface (stack traces, `console.log` timing) differs from a full Node process, so troubleshooting techniques familiar from Node-based platforms don't transfer directly.
- Some `wrangler` sub-command flag details (exact `rollback`/`tail`/`secret put` flags) are only documented on deep per-command pages, not the command index — worth confirming exact syntax before scripting automation around them.

## Operational Story

- **Preview deploys**: Not automatic out of the box the way Vercel/Netlify PR previews are. Use `wrangler versions upload` to create a preview version with its own URL, then `wrangler versions deploy` to promote it to production traffic — this needs to be wired into the GitHub Actions workflow manually (the tech-stack hint already specifies `ci_provider: github-actions`, `ci_default_flow: auto-deploy-on-merge`).
- **Secrets**: Managed via `wrangler secret put <NAME>` (stored encrypted in Cloudflare, not in `wrangler.jsonc`); readable only by the account/token that deployed the Worker. Local dev uses `.dev.vars` (gitignored, per this project's existing convention). Rotation = re-run `wrangler secret put` with the new value; verify the `astro:env`/`wrangler vars` gotcha above doesn't cause the new value to silently fail to propagate to `astro:env`-based reads.
- **Rollback**: `wrangler rollback [deployment-id]` reverts to a previous Worker version; `wrangler versions list` shows the history. Fast (seconds), but Supabase schema/data changes do not roll back with it — any DB migration tied to a bad deploy needs its own manual reversal.
- **Approval**: Human-only — rotating the primary `SUPABASE_KEY`, changing billing tier, or deleting the Worker/project. An agent may run `wrangler deploy`, `wrangler versions upload`, and read-only `wrangler tail`/log queries unattended once secrets and CI are configured.
- **Logs**: `wrangler tail` streams live production logs from the terminal; the GA remote MCP server at `https://observability.mcp.cloudflare.com/mcp` (OAuth-backed) gives structured, queryable access to logs/analytics for an agent without parsing CLI text output.

## Getting Started

1. Confirm the current adapter config is production-ready: `astro.config.mjs` already has `adapter: cloudflare()` and `output: "server"` — no adapter change needed.
2. Install/update Wrangler if not already present: `npm i -D wrangler` (verify version supports `nodejs_compat_v2` and `--x-autoconfig`; check `npx wrangler --version`).
3. Generate or verify `wrangler.jsonc` exists with a `compatibility_date` set explicitly (do not leave it to drift) and `nodejs_compat` flags as needed for Supabase's SSR client.
4. Set secrets for production: `npx wrangler secret put SUPABASE_URL` and `npx wrangler secret put SUPABASE_KEY` (matches the `envField` schema already declared in `astro.config.mjs`); keep `.dev.vars` for local dev as already gitignored.
5. Build and deploy: `npm run build && npx wrangler deploy`. Verify with `npx wrangler tail` to confirm the deployed Worker serves requests and reads env vars correctly (specifically re-test the `astro:env` gotcha against this project's Supabase client init in `src/lib/supabase.ts`).
